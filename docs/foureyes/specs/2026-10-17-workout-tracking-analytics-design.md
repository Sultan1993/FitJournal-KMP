# Workout tracking + exercise logging analytics — design spec (2026-10-17, revision 3)

Chosen approach: entry 1 merged with 2 (explicit, compile-enforced threading of provenance through the carriers each platform already has; shared catalog, calculations and classification in KMP). I agree with the choice; nothing below argues against it.

This extends `2026-10-16-analytics-harness-design.md`. Every Cross-Task Contract and Global Constraint of that spec still applies unless a line below changes it explicitly (deliberate changes: `EndWorkoutUseCase` gains a `RecordRepository` and its two-argument constructor is replaced by an explicit three-argument one; `createWorkoutViewModel` is replaced, not overloaded; `RecordRepository.replaceExerciseInRecord` and `RecordRepository.deleteRecord` return `Boolean` — all so that a forgotten call site is a compile error or an unreported/duplicated write is impossible, which is the point of the chosen approach).

## Revision notes

- **Target commits omit LAST_TIME / PREVIOUS_SET** — fixed. `handleCommitTarget` maps all four `SeedSource` values (OWN→`unchanged`, LAST_TIME→`prefill_last_time`, PREVIOUS_SET→`prefill_previous_set`, NONE→`default`); Task 3 test `commitTarget_logsActionCommitTarget_forAllFourSeedSources` asserts each, reusing the `WorkoutFocusCommitTargetTest` fixtures (last-session inheritance; `oneLoggedOneTarget`).
- **p15 and UG-2 lack target rows** — fixed. Catalog adds create `sets = emptyList()`, so p15 now copies an earlier day's workout (`exercise_added{source=copy, entry=copy}`) to obtain target rows with a prior occurrence, then commits one (`prefill_last_time`, `same`), types into the second (`typed`, `lower`) and re-saves the first (`unchanged`, `same`); UG-2 gains an explicit "copy an earlier day" preparation step before the swipe-commit. Expectations recomputed (07, 10, 12 change).
- **Picker attribution across the report boundary** — fixed. Cookbook 09 computes `LEAD` over all opens in `events` (through `@observed_through`) and restricts *reported* opens to those present in `window_events`; `tracking_aug` now has `@end_date` 08-30 < `@observed_through` 08-31, and new persona p17 carries the 23:50 open / 00:00 reopen / 00:05 completion boundary case (the August open is abandoned).
- **Removal rereads cannot guarantee one emission** — fixed with the authoritative-result pattern already used by `addSet`/`deleteSet`/`replaceExerciseInRecord`: `RecordRepository.deleteRecord` returns `Boolean` (`true` only when this call tombstoned a live row, atomically); both VMs emit `exercise_removed` only on `true` from the exercises captured before the write, no re-read. Covers a duplicate concurrent request (one `true`) and a row deleted before the local write (sync or otherwise: `false`, nothing emitted) — the brief's no-op constraint now holds. The former `deleteRecord` non-goal and the "one RecordRepository change" constraint are revised.
- **`created_custom` conflicting rules** — fixed. Both platforms keep an explicit per-picker-session created-id ledger fed only by the create flow (iOS `ExercisePickerSession` owned by `ImportCoordinator`; Android `ImportDataStore.markCreated` fed through a new `ExerciseCreatedListener` bound to the store), with one precedence: any committed id in the ledger → `created_custom`, else the screen's own value (`browse`/`search`). A synced exercise arriving mid-session is never `created_custom` on either platform.
- **Single pending-open flag loses opens** — fixed. `WorkoutViewModel` keeps a queue of `(date, entry)` open requests; on the first non-loading state the queue is drained: the state's own date emits from the shown page, a superseded date (its read cancelled by `flatMapLatest`) emits with `workout_number = 1` and `session_state` read from `sessionRepository.getSessionByWorkoutNumber`. Emission count = construction + distinct-date selections regardless of read timing; new test `workoutOpened_emitsEveryRequest_whenSelectionsOutrunTheRead`.
- **Orphan query measures window imbalance** — fixed. The net-balance query is dropped; new cookbook `13_rest_orphans` implements mature-start pairing (post-change starts only — `trigger IS NOT NULL`; `ended` looked up in `events` within `(start, min(next start, start + duration + 60 s)]`; starts whose deadline exceeds `@observed_through` are `immature` and excluded), with p16 (legacy start, excluded) and p17 (cross-boundary paired start + a true orphan) as fixture boundary cases. Total cookbook runs: 19.

## Purpose

Answer, from raw `events_*` rows, how workouts are actually tracked: live vs backfilled logging, built from scratch vs routine (copy/repeat), where the exercise picker is abandoned, whether prefilled values are accepted and whether users progress vs last time, how big sessions are and how many end empty, and how much the side door (exercise details → calendar) is used. The data consumer is Claude via `bq`; correctness (no duplicate emissions, no missing emissions, iOS/Android parity, stable join keys, closed vocabularies) outranks everything else.

## Assumptions

Decisions made without asking the user; what breaks if wrong.

- **`focus_opened.entry` is derived, not threaded.** Every Focus open comes from the Workout screen's three `OpenExerciseFocus` dispatch sites (`WorkoutPageContent.kt:121/124/130`); `startAddingSet=true` is exactly the "Add set" tap, everything else is a row tap. The VM derives `row_tap`/`add_set` from its own `startAddingSet` parameter and emits `next_exercise` itself when `FinishExercise` advances. A fourth native entry to Focus would inherit `row_tap` (under-labels, never miscounts).
- **`workout_opened.entry` vocabulary is {home_start, details_edit, calendar}.** These are the only routes that open the workout pager today: iOS `StartPoint.workout` and the two `openWorkout(for:workoutNumber:)` sites; Android `HomeViewModel.openWorkout()` and `WorkoutDetailsHostViewModel.onOpenEdit`. Repeat lands through the Edit route and is identified by the `exercise_added{source=repeat}` that precedes it. The brief's `history`/`list`/`calendar_add` do not exist as routes.
- **`exercise_added.entry` has no `exercise_info` member.** Both platforms have exactly one side-door flow — details/info screen → "Add to workout" → calendar sheet → add — with a single construction/navigation site each (`ExerciseInfoViewController.swift:144`, `ExerciseDetailsViewModel.kt:139`); the info screen never adds by itself. The flow emits `exercise_calendar`. If a second side door is ever built it gets its own enum member; nothing is mislabelled today.
- **`set_logged.input` gains `unchanged`** (brief vocab + 1): re-saving a filled row without typing is neither a prefill nor typing.
- **`rest_timer_ended.outcome` gains `restarted`** (brief vocab + 1): a `start()` while running replaces the rest silently today; `restarted` keeps every `rest_timer_started` paired with exactly one `rest_timer_ended` within a process.
- **A rest that outlives its process never emits `rest_timer_ended` (scoped exclusion, both platforms).** iOS has no resume: the rest dies with the process and its `started` stays unmatched. Android `resume()` adopts the persisted deadline but the store holds only the deadline (`TIMER_LAST_END`), not the start moment or trigger, so any `elapsed_sec`/`trigger` for the resumed remainder would be fabricated; it therefore tracks nothing and its later stop/expiry tracks nothing. Impact is bounded (exposure ≤ `duration_sec` per rest, only when the OS kills the app mid-rest) and measured from data by cookbook `13_rest_orphans` (mature-start pairing; legacy starts excluded), not guessed. If the orphan rate ever matters, the fix is an Android-only store extension (start + trigger), scoped out here.
- **`found_via` is absent** on `exercise_added` for `copy`/`repeat`/`exercise_calendar` (no picker) and never on the typed replace routes. **`created_custom` = at least one committed exercise id is in the picker session's created-id ledger** (iOS `ExercisePickerSession`, Android `ImportDataStore`), which only the create flow feeds; it takes precedence over the screen's own value, otherwise `browse` (list screen) or `search` (search screen). An exercise that appears through sync during the session is never `created_custom`.
- **`exercise_removed` is one event per removed exercise**; a superset record deleted from the Workout screen emits N events. **Removal no-op guard is the repository's result**: `deleteRecord` returns `true` only when this call tombstoned a live row; the VMs emit for the exercises captured before the write iff it returned `true`. A row deleted before the write (sync pull, a duplicate tap) returns `false` and emits nothing.
- **`workout_session_end.exercise_count`/`set_count` are absent when the post-end read fails** (`runCatching`); the discard-empty path writes literal zeros (nothing to read).
- **Day context uses the device-local calendar day** at emission time (`days_from_today = today.daysUntil(date)`, negative = past).
- **Pre-change events are told apart by a missing field, never a sentinel.** Every cookbook query reading a new param on a pre-existing event `COALESCE`s to `'unknown'` and reports that bucket as its own row whenever it is non-empty; cookbook 13 excludes `rest_timer_started` rows without `trigger` entirely because a legacy start can never be paired.
- **GA4 limits hold:** `set_logged` grows to 13 params, `exercise_added` to 11; well under 25.

### Data flow

1. **Day context.** Every slot-carrying write event (`exercise_added`, `set_logged`, `workout_session_start/end`, `workout_opened`) carries `day_kind` + `days_from_today` from `dayContextOf(workoutDate, today)` at the emission site. Shared use cases take `today: () -> LocalDate` (defaulted to `::systemToday`; tests inject a fixed day); the VMs use their existing `clock`/`timeZone`. Native sites call `dayContextOf(date)`.

2. **`workout_opened`.** `WorkoutViewModel` takes `entry: WorkoutEntry` (required) and keeps `pendingOpens: ArrayDeque<Pair<LocalDate, WorkoutEntry>>`, seeded with `(initialDate, entry)` at construction. `SelectDate(date)` with `date != selectedDate.value` appends `(date, CALENDAR)` (same-date re-select: nothing; `onDateSelected` already resets `currentPageIndex` to 0). In the state `collect`, when the built state has `loading == false`, `selectedDate == selectedDate.value` and the queue is non-empty, the queue is drained in insertion order, one event per entry: an entry whose date equals the state's date emits from the shown page — slot = `(journalId, date, page.workoutNumber ?: 1)`, `session_state` = `RUNNING` iff `runningSession != null && runningSession.journalId == journalId && runningSession.date == date && runningSession.workoutNumber == page.workoutNumber`; else `FINISHED` iff `page.session?.endedAt != null`; else `NONE`; an entry whose date differs was superseded before its read completed (`selectedDate.flatMapLatest` cancelled it) and emits with `workoutNumber = 1` (a calendar pick always lands on page 0) and `session_state` from `sessionRepository.getSessionByWorkoutNumber(uid, jid, date, 1)`: `null` → `NONE`, `endedAt == null` → `RUNNING`, else `FINISHED`; a throwing read → `NONE`. The queue is empty afterwards, so later states for the same date (record changes) emit nothing. Emission count therefore equals construction + number of distinct-date selections, regardless of read timing or StateFlow conflation. Opening a finished past workout while today's session runs reads `finished`, and a second workout of the same day reads `none`. iOS supplies `entry` through the replaced factory (`homeStart` for `StartPoint.workout`, `detailsEdit` for both `openWorkout(for:)` callers); Android through a required `PARAM_ENTRY` path argument produced only by `workoutGraphRoute(entry, …)` (`HomeViewModel` → `HOME_START`, `WorkoutDetailsHostViewModel.onOpenEdit` → `DETAILS_EDIT`).

3. **Picker provenance (catalog adds / replaces).**
   - iOS: `ExerciseOpenPurpose.importing(Date, workoutNumber:, entry:)` / `.replacing(WorkoutRecord, entry:)`. `WorkoutCoordinator:261` passes `ExerciseEntry.workoutButton`, `:412` `ExerciseEntry.focus`, `:253` `ExerciseEntry.replaceWorkout`, `:424` `ExerciseEntry.replaceFocus` (always type-qualified so parity is grep-able). `ImportCoordinator.setupExerciseImport()` tracks `ExercisePickerOpened(entry)` — the single picker-open site — and creates a fresh `ExercisePickerSession` (the created-id ledger) that it injects into both `ExerciseListViewModel` (`:123`) and `ExerciseSearchViewModel` (`:166`) as `pickerSession`; `ExerciseCoordinator` (browsing) passes `nil`. The list VC's `CreateExerciseDelegate.createExercise(_:didCreateExercise:)` dispatches `.exerciseCreated(exercise)` before `.reload`; the list VM forwards the id to `pickerSession.markCreated`. At commit both VMs compute `foundVia = pickerSession.foundVia(committing: ids, else: .browse / .search)` — `.createdCustom` iff any committed id is in the ledger, else the fallback. Both call `importExercises.execute(date:workoutNumber:exercises:entry:foundVia:)` / `replaceExerciseInRecord.execute(record:exercise:entry:foundVia:)` → `DefaultImportRecordRepository`, which emits `exercise_added{entry, found_via, day}` at the existing site and `exercise_replaced` iff the shared `replaceExerciseInRecord` returned `true`. `ExerciseDetailsCalendarViewModel.addToWorkout` passes `ExerciseEntry.exerciseCalendar, nil` (the only side door; `ExerciseInfoViewController` is untouched).
   - Android: `ImportDataStore.setAction` is **deleted**; `startExercisePicker(action, entry)` sets action+entry, resets `imported`/`workoutNumber`/`createdIds` exactly as `setAction` reset its fields, and tracks `ExercisePickerOpened(entry)`; `startCopyPicker()` sets `IMPORT` with no entry, the same resets and no event (the records/copy picker is not an exercise picker). `ImportDataStore` implements `ExerciseCreatedListener` (`onExerciseCreated(id)` = `markCreated(id)`); `CreateExerciseUseCase` (feature/exercises) takes the listener and calls it after create + fetch succeed; `WorkoutModule` binds the listener to the `ImportDataStore` singleton the picker VMs inject. `WorkoutCmpHostViewModel.navigateToImportFromList` → `(IMPORT, ExerciseEntry.WORKOUT_BUTTON)`, `navigateToImportFromWorkout` → `startCopyPicker()`, `navigateToReplace` → `(REPLACE, ExerciseEntry.REPLACE_WORKOUT)`; `ExerciseFocusHostViewModel.onOpenAddExercise` → `(IMPORT, ExerciseEntry.FOCUS)`, `onOpenReplaceExercise` → `(REPLACE, ExerciseEntry.REPLACE_FOCUS)`. List/Search VMs read `importDataStore.getEntry() ?: return` beside `getAction() ?: return` and compute `foundVia = if (ids.any { it in importDataStore.getCreatedIds() }) CREATED_CUSTOM else BROWSE / SEARCH`. `ExerciseDetailsCalendarViewModel` passes `ExerciseEntry.EXERCISE_CALENDAR, null`.
   - Shared: `ImportWorkoutViewModel` (COPY) and `RepeatWorkoutUseCase` (REPEAT) emit `exercise_added` with `entry = COPY/REPEAT`, `foundVia = null`, day context via `today`.

4. **Set provenance (shared Focus VM).** `FocusInputState` gains `seedInput: SetInput` and `edited: Boolean`. Only `withFocusedText` sets `edited = true`. Every (re)seed sets `edited = false` and `seedInput`: `buildInput(exercise, set, mode)` maps `seedValuesAt(...).source` → add mode: OWN→`PREFILL_PREVIOUS_SET`, LAST_TIME→`PREFILL_LAST_TIME`, PREVIOUS_SET→`PREFILL_PREVIOUS_SET`, NONE→`DEFAULT`; edit mode: OWN→`UNCHANGED`, others as above. The post-log re-arm sets `seedInput = PREFILL_PREVIOUS_SET, edited = false`; `handleFocusField` copies keep both. At commit: `input = if (edited) TYPED else seedInput`. `handleCommitTarget` passes `action = COMMIT_TARGET` and `input` from `focusEditorSeed(owner, set).source` with the full map OWN→`UNCHANGED`, LAST_TIME→`PREFILL_LAST_TIME`, PREVIOUS_SET→`PREFILL_PREVIOUS_SET`, NONE→`DEFAULT` (a target commit inherits last session's aligned set when one exists, else the previous committed set — `WorkoutFocusCommitTargetTest` already pins both). **`in_session`** = `runningWorkoutNumber == workoutNumberOf(recordId)` where `runningWorkoutNumber: Int?` is the running session's `workoutNumber` when it is on this journal+date (null otherwise), refreshed at the same two sites as `sessionRunningHere` (`refreshSessionRunningHere`, `observeRunningSession`); `sessionRunningHere` itself is unchanged. `vs_last_time` is computed inside `AddSetUseCase`/`UpdateSetUseCase` by `vsLastTime(exercise, setIndex, topValue, bottomValue)` against `exercise.lastOccurrence?.setAt(setIndex)` (Focus loads with `includeLastOccurrence = true`).

5. **Deletions / removals / replacements.** `DeleteSetUseCase` emits `set_deleted{…, was_logged}` only when the repository returned `true`. `RecordRepository.deleteRecord` returns `true` only when this call tombstoned a live (non-deleted) record — the existence check and the soft delete happen atomically in the repository, so of two concurrent calls on one record exactly one returns `true`, and a record already removed (by sync or an earlier call) returns `false`. `exercise_removed` is emitted by `WorkoutViewModel.onDeleteRecord` (`WORKOUT`: `record.exercises` captured before the call, one event each, `had_sets = exercise.hasLoggedSets`) iff `deleteRecord` returned `true`, then `pruneEmptiedPage` as today; and by `WorkoutFocusViewModel.handleRemoveExerciseConfirmed` (`FOCUS`, already serialized by `isMutating`) iff its `deleteRecord` call — on the single-exercise record, or on the split-off record after `removeExerciseFromSuperset` — returned `true`. No post-write re-read is involved. `exercise_replaced` is native, gated on the repository's `Boolean`.

6. **Sessions.** `StartWorkoutUseCase` adds day context (still emits only on create/revive). `EndWorkoutUseCase(sessions, records, syncTrigger, tracker, today)` after `endSession` reads `records.getRecordsByDate(userId, journalId, date, includeLastOccurrence = false)` filtered to the ended `workoutNumber`: `exercise_count = Σ exercises.size`, `set_count = Σ sets.count { isLogged }`; `runCatching` → both absent on failure. `FinishForgottenSessionUseCase` does the same for `via = auto`. **Discard-empty:** `WorkoutViewModel.onRequestEndSession` keeps `endRequestInFlight`; it returns at once when set, sets it before launching and clears it in `finally`. In the no-records branch, after `sessionRepository.deleteSession` returns normally (before `clearWorkoutNote`), it tracks `WorkoutSessionEnd(jid, running.date, running.workoutNumber, running.durationSec(clock.now()), DISCARD_EMPTY, dayContextOf(running.date, today()), exerciseCount = 0, setCount = 0)`. A thrown `deleteSession` emits nothing.

7. **Rest timer.** Inside the lane: `Cmd.Start(info, trigger)`; `start()`/`toggle()` → `MANUAL`, `autoStart()` → `AUTO`. State: `runStartedAt`, `runDuration`, `runTrigger`, `resumed`. `Start` while `Running && !resumed` first tracks `RestTimerEnded(RESTARTED, elapsed, runDuration, runTrigger)`, then starts and tracks `RestTimerStarted(duration, trigger)`. `Stop` → `STOPPED`; `Tick` expiry → `FINISHED` (`elapsed = duration`); both skipped while `resumed`. `Resume` sets `resumed = true`, tracks nothing (Assumptions). `elapsed_sec = ((now − runStartedAt) + 500) / 1000` clamped to `[0, duration]`.

8. **Focus.** `WorkoutFocusViewModel` tracks `FocusOpened(slot, recordId, exerciseId, entry, startAddingSet)` once, the first time `republish()` resolves an active record/exercise (`hasResolvedActive` false→true), `entry = if (startAddingSet) ADD_SET else ROW_TAP`; and again with `NEXT_EXERCISE` inside `handleFinishExercise` when `next != null`. Picker/member switches are not tracked.

9. **Custom exercises.** `CreateExerciseUseCase` ×2 track `CustomExerciseCreated(exerciseId, resultType, category = primaryCategory.type)` after create + fetch succeed; Android additionally notifies `ExerciseCreatedListener`, iOS reaches the ledger through the list VC delegate (step 3).

### Error handling

Unchanged from the base spec: emit only after a successful write, never on no-ops; every tracker call `runCatching`-wrapped inside `Analytics`; nothing throws across SKIE. New specifics: a thrown `getRecordsByDate` in `EndWorkoutUseCase` drops only the counts; `replaceExerciseInRecord == false` emits nothing (the record or member vanished while the picker was open); `deleteRecord == false` emits nothing (already gone — sync, or a duplicate request that lost the race); `DeleteSetUseCase` returning `false` emits nothing; a thrown `deleteSession` in the discard path emits nothing; `workout_opened` for a date waits for the first non-loading state or its supersession, so a VM disposed before any data loads emits nothing; a throwing `getSessionByWorkoutNumber` on the superseded path labels `session_state = none` rather than dropping the open.

### Analysis layer

- `README.md` Conventions gains: day context; provenance (`input` rule incl. the four-way target-commit map, `vs_last_time` comparison order incl. the null/zero rules, `in_session` slot scoping); the **missing-field = pre-change rule**; the **rest-timer pairing rule** (one `ended` per `started` within a process; a rest that outlives its process emits no `ended` on either platform; the orphan rate is measured by cookbook 13 — mature starts with `trigger` only, `ended` looked up through `@observed_through`); the **picker-attribution rule** (an add/replace completes the latest preceding open of the same user+entry if within 30 min; an open followed by another open before any add is abandoned — the successor may lie beyond `@end_date`; opens within 30 min of the end of `@observed_through` are immature and excluded); the **superseded-open rule** (a calendar pick that outruns the previous read still emits, with `workout_number = 1` and a session-table `session_state`); the removal rule (emitted only on a confirmed tombstone); the discard-empty rule (`via = discard_empty` ⇒ counts are literal zeros); the **`created_custom` ledger rule** (precedence over browse/search). Custom-definition list gains `day_kind`, `found_via`, `input`, `vs_last_time`, `in_session`, `session_state`, `was_logged`, `had_sets`, `start_adding_set`, `trigger`, `category`. A **UG-2 checklist** section (Task 10) with UG-1's evidence-file format.
