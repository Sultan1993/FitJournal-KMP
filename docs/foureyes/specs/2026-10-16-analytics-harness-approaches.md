# Analytics harness + 5 funnels — approaches (2026-10-16)

Brief: product-analytics harness from scratch (Firebase-backed, shared KMP catalog used by iOS, Android and CMP screens), event catalog, the 5 most important funnels as GA4 Explore steps + BigQuery SQL. Addendum (user): the data exists so Claude can later analyze user behavior from raw events.

## Proposed

### 1 — Dictionary file is truth; Kotlin catalog generated from it; native sinks
WHAT: Same sinks, holder, VM wiring, screen views, call sites, funnels and cookbook as entry 3, but the source of truth is a hand-authored `Multiplatform/docs/analytics/events.yaml` (name, meaning, when-fired, params with type/vocab/description, funnel membership, user properties). A Gradle task generates `build/generated/analytics/AnalyticsEvents.kt` and `events.json`, wired via `kotlin.sourceSets.commonMain.kotlin.srcDir(generatedDir)`. jvmTest validates GA4 limits over the YAML.
COST: No runtime deps; codegen task on the KMP build path (runs on every iOS Xcode build); no YAML parser in tree (author JSON, or add build-script-only `kaml`).
GIVES UP: Typed Kotlin ergonomics for anything the generator doesn't model; reviewers review generated code; ordering invariants only stated, not enforced.
CHECKED: Firebase/BigQuery as entry 3; `srcDir` generated sources = standard KGP capability (not re-queried); `kaml` unverified for current Kotlin.

### 2 — Kotlin catalog is truth, one shared GitLive sink instead of two native ones
WHAT: Catalog, jvmTest-rendered dictionary, fixtures and cookbook as entry 3; `Analytics` calls `dev.gitlive:firebase-analytics` from commonMain, no platform sinks, `:common:analytics` deleted. iOS framework gains `linkerOpts("-framework","FirebaseAnalytics")` + `-F` into SPM `$(BUILT_PRODUCTS_DIR)`.
COST: New dependency pinned to GitLive's Firebase versions; Kotlin 2.4.20 (SKIE ceiling) / Firebase iOS 13 compatibility unverified; K/N-framework-vs-SPM link wiring is a known rough edge.
GIVES UP: Control of the iOS binding; second third-party ceiling on the shared module; one break kills analytics on both apps.
CHECKED: GitLive `firebase-analytics` API + appleMain actual over FIRAnalytics; migration guide says Firebase iOS must be supplied by app via CocoaPods/SPM (Context7 /gitliveapp/firebase-kotlin-sdk). Linker wiring + Kotlin 2.4.20 compat unverified.

### 3 — Kotlin catalog is truth; dictionary + SQL fixtures generated from it; native sinks
WHAT: `Multiplatform/shared/src/commonMain/kotlin/kz/maestrosultan/fitjournal/analytics/`: sealed `AnalyticsEvent` catalog, each case = GA4 name + typed params (Long/Double/String, fixed-vocab strings, join keys journal_id, workout_date YYYY-MM-DD, workout_number, record_id, exercise_id, set_index; no free text), `screenView(name)`, user properties (sub_tier, quota_state, workouts_used bucket), `setUserId(firebaseUid)`. Non-suspend `AnalyticsSink` + process-wide `Analytics` holder (`install(sink)`, no-op before install, `runCatching` on every call) following `domain/user/UserSession.kt` / `domain/quota/FreeQuotaSettings.kt`. Each case carries `meaning` + per-param descriptions; jvmTest `AnalyticsCatalogTest` enforces GA4 limits AND renders `Multiplatform/docs/analytics/events.json`, failing if the checked-in file differs. Sinks: iOS `FitJournal/Analytics/FirebaseAnalyticsSink.swift` (SPM FirebaseAnalytics already linked); Android `:common:analytics` rebuilt as Hilt `FirebaseAnalyticsSink`, installed from `FitJournalApplication`. Shared VMs take `tracker: AnalyticsTracker = Analytics` default param (pattern `WorkoutListViewModel.kt:57-64`); CMP screens call `TrackScreenView("...")` (DisposableEffect). Native call sites: AuthUserUseCase ×2, HomeViewModel, HomeViewController, QuotaPaywall, Superwall delegates, the three setEntitled sites per platform. Old iOS/FitJournal/Analytics/* and Android common/analytics/{domain,data,di} deleted. Analysis layer in `Multiplatform/docs/analytics/`: events.json (generated), README (conventions, enabling BigQuery export, `bq` usage), funnels.md (5 GA4 Explore funnels), cookbook/*.sql (5 funnels + D1/D7/D30 retention, weekly-active cohort, paywall conversion by quota_state, feature adoption), fixtures/ (stdlib Python generator emitting GA4-export-shaped NDJSON personas from events.json, `bq load` into throwaway `analytics_fixture.events_YYYYMMDD` so every cookbook query executes and asserts expected counts).
COST: No new deps. ~10 KMP files + jvmTest, 2 sinks, ~20 native call-site edits, 4 VMs, 4 CMP screens, 12 deletions, ~12 doc/SQL/fixture files, 1 Python script. Needs user to enable BigQuery export and allow a fixture dataset (or dry-run-only fallback).
GIVES UP: Firebase binding written twice (~30 lines each); dictionary is generated JSON (descriptions live in Kotlin literals); fixture SQL proves shape, not emission (DebugView smoke check covers that).
CHECKED: Firebase SCREEN_VIEW/SCREEN_NAME/SCREEN_CLASS, setUserId, setUserProperty (24/36 chars, 25 max), logEvent limits (500 names, 25 params, 40-char names, 100-char values, reserved prefixes) — Context7 /websites/firebase_google. GA4 export layout (analytics_<property_id>, events_YYYYMMDD, events_intraday_* only with streaming, UNNEST event_params, _TABLE_SUFFIX) — support.google.com/firebase/answer/7029846. Non-suspend interface avoids SKIE `__` async requirement.

### 4 — Shared catalog and tracking contract, native Firebase delivery
WHAT: Typed catalog, screen names, user properties, validation and a non-suspending tracking interface once under `Multiplatform/shared/src/commonMain/kotlin/kz/maestrosultan/fitjournal/analytics/`; native implementations injected via Hilt and existing Swift construction paths; failures contained at the boundary, Firebase handles delivery, tracking never awaits connectivity. Instrument at successful action boundaries in `domain/workout/usecase/`, `ui/workout/main/WorkoutViewModel.kt`, `ui/workout/focus/WorkoutFocusViewModel.kt`, list/details. Lifecycle-aware screen impressions with ONE owner per screen (no duplicate native-host + CMP reporting). Native hooks: auth, home meter, rest timer, subscription via `iOS/FitJournal/Workout/WorkoutCoordinator.swift`, `QuotaPaywall.swift`, Android `WorkoutCmpHostViewModel.kt`, both `SuperwallController`s. Five questions: activation to a second logged workout within 7 days; quota-to-paid conversion segmented by meter-card vs gate entry; workout execution and completion; repeat training across days/weeks; Focus adoption via actual set logging and reuse (timer/history supporting). Keep "logged a workout" distinct from "finished a timed session" (records can exist outside a session); quota counts workout slots (`domain/quota/WorkoutQuota.kt`). Firebase uid as identity, cleared with account properties on logout; no email/notes/free text. Purchase outcomes from Qonversion's result path; Superwall callbacks = exposure; RevenueCat stays observer. Delete `iOS/FitJournal/Analytics/` and `Android/common/analytics/`. Docs (catalog, 5 GA4 Explore recipes, BigQuery SQL, console setup) in `Multiplatform/docs/`; catalog verification in `shared/src/jvmTest/`.
COST: No new SDK/backend/migration. ~70–90 files across 3 repos on feature/analytics. Event names become a reporting contract. GA4 custom definitions + BigQuery linking are console steps.
GIVES UP: Guaranteed delivery / financial ledger (best-effort client analytics); acquisition starts at first_open; existing users must be separated from new activation cohorts; no historical backfill; GA4 Explore and BigQuery counts not promised identical.
CHECKED: Context7 — Firebase event APIs/limits, SKIE suspend bridging, Superwall presentation callbacks (iOS + Android), Qonversion entitlement results, GA4 Explore sequence/time constraints, BigQuery event schema; official docs on manual screen reporting, offline buffering, no export backfill.

## Decisions

- Proposers: Fable → 1, 2, 3 (revised after the user's analysis addendum; its pre-addendum set had a "catalog as data only, host-callback trackers" entry it withdrew itself as unable to guarantee consistent params). Sol → 4 (Sol ran on the pre-addendum brief).
- Own picks: Fable VERDICT = 3. Sol VERDICT = 4.
- Merge: 3 + 4 are the same architecture (KMP catalog + non-suspend interface + native Firebase sinks, delete legacy). Merged as **3**, carrying 4's distinct content: one screen-view owner per screen, meter-card vs gate entry segmentation, logged-workout ≠ finished-session, quota = workout slots, identity + properties cleared on logout, purchase outcome from Qonversion's result path (Superwall = exposure), existing-user cohort separation, no backfill.
- Dropped: 2 (GitLive) — dominated by 3: same catalog and analysis layer, adds an unverified dependency against the Kotlin 2.4.20/SKIE ceiling and an iOS link-wiring risk, for no requirement the brief states.
- Unknown dropped as answered by evidence: "one GA4 property or two?" — both apps' configs carry project_id `fit-journal-pro` (iOS GoogleService-Info.plist PROJECT_ID, Android google-services.json), and a Firebase project links to one GA4 property → one dataset with a `platform` column.
- Unknown below the bar → spec Assumption: daily `events_*` export only (streaming/intraday not required; funnels/retention are day-grain).
- Recommendation: 3 (merged).
